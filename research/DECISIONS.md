# Decisions

Each entry: what I decided, and why. Newest at the bottom.

- **D1. Ran the prompt, recorded first.** The chat message was only the pasted prompt, so I asked once whether to run it. The answer was "Run it, record first", so the 5-minute clip was recorded before the videos (still "before changing anything", as the prompt asks).
- **D2. Worktree from origin/main, upstream removed.** `git worktree add -b feat/classroom-vision ..\ARGOS-vision origin/main` (origin/main = 95f7811, the "remove desk boxes" merge). Git set the new branch to track origin/main; I ran `git branch --unset-upstream` so a stray `git push` can't go anywhere.
- **D3. Watch skill: Gemini failed, used the local engine.** The skill was configured for Gemini (key present). Attempt 1: gemini-3.7-flash HTTP 503 (overloaded), twice. Attempt 2: other models, gemini-2.5-flash 404 (retired), gemini-3.8-flash 503. After those 2 setup attempts I set up the local engine inside the sandbox (ffmpeg + ffprobe from the `ffmpeg-binaries` PyPI wheel, `yt-dlp` from PyPI, both in `.venv-sandbox`, put on PATH only for the watch process). All 8 videos then processed with captions + keyframes. I did not change `~/.config/watch/.env`.
- **D4. Watch detail = efficient, 16 frames per video, captions only.** Enough to confirm what each video shows; every video had captions, so no speech-to-text was installed. Where a claim rests only on captions I wrote "said"; where I saw it in a frame, "shown".
- **D5. Existing AGPL models kept for the baseline.** The repo already runs `yolo11n-pose.pt`, `yolo11n.pt`, `yolov8s-worldv2.pt` (Ultralytics, AGPL-3.0). The baseline must use them, so I copied them from the main checkout (read only) into `models\`. Any **new** model I download must be Apache-2.0 / MIT / BSD; AGPL does not count as "similar" for new downloads.
- **D6. Skipped graphify.** The repo is ~20 source files; I read the files directly. A graph would add an untracked `graphify-out/` folder to the branch for no gain.
- **D7. The clip came out at 3.85 camera fps, not 30.** The recorder asks for MJPG 1080p @ 30, but it encoded every frame to MJPG at quality 90 and drew a preview in the same thread, while the watch skill was decoding videos in the background. The user had left the camera by the time I saw the rate, so I kept the clip. Effect: frames are ~260 ms apart, so between-frame tracking is tested on bigger jumps than the live camera would give (harder, not easier). Timestamps per frame are in `classroom_times.json` and the brain is fed those real times.
- **D8. Ground truth = helper model + my own check, boxes only.** A bigger, separate detector (RT-DETRv2-R50, Apache-2.0, never used by the app) proposes person/phone boxes on the full frame (tiles were tried but took ~30 s per frame on this CPU, so dropped); I then check every review frame by eye and fix: remove false boxes, add missed people, and draw the items (watch, headphones, paper, pen, phone) by hand on a 200 px grid. Hand-drawn item boxes are rough, so an item counts as found if the boxes overlap (IoU >= 0.2) or the found box's centre is inside the true box grown by 30%. Only box numbers are stored (`research/labels/gt.json`), no pictures.
- **D9. Distance in metres is an estimate.** No calibration target was recorded. I estimated the camera focal length at ~900 px (the person at the desk, ~0.7 m away, has ~0.45 m of shoulders covering ~580 px), and convert a person box height h (px) to distance = 900 x 1.0 m / h (about 1.0 m of a seated person is visible). Bands: near < 2 m, mid 2-6 m, far > 6 m. Treat the metres as +/- 30%.
- **D10. OpenVINO telemetry turned off.** The `openvino` wheel pulls in `openvino-telemetry`; I ran `opt_in_out --opt_out` right after install so nothing is sent out (the prompt forbids sending data to outside services).
- **D11. Keep rule for in-between rounds.** The baseline runs at 0.25 FPS, so no single change can bring FPS to 15 in one step, and "FPS stays at 15 or more" could never be met. I kept a change when accuracy improved, FPS did not drop, and every alert that fired before still fired. The 15 FPS target stays a stop condition; it was **not** met.
- **D12. Real-time replay instead of every-frame replay.** Replaying every frame took ~2.5-4 s per frame (~48 min per run). The live app drops frames when it is slow, so the harness now does the same: the clip plays at recorded speed, the program takes the newest frame when it is free, and each labeled frame is scored on the result that was on screen at that moment. Every run takes ~5 min and the numbers are what a proctor would actually see.
- **D13. Items all count as "near".** Every labeled item sits on the near desk or in the near person's hands (< 2 m), so item recall is reported in the near band only. No far items were in the clip, so I can't report a working distance for items beyond ~1.5 m.
- **D14. Round 2 reverted even though people tracking improved.** Person recall +5 points, overlap ID switches 0.87 -> 0.73, face dropout 36.8% -> 21.1%, FPS x4. But items only came out on AI-check frames, so what was on screen had no items (recall 0) and round 1's phone alert stopped firing. The rule says revert. The obvious fix (hold the last items until the next AI check) would be the same idea's second attempt; there was no time left for it. Patch kept at `research/round2_tracker.patch`.
- **D15. flask installed into the sandbox.** `tests/test_main.py` imports the dashboard, which needs flask (already in requirements.txt). Installed `flask==3.1.2` from PyPI into `.venv-sandbox`.
- **D16. No alert thresholds touched.** Nothing in `settings/config.py` was changed. No threshold suggestions came up.

## Run 2: branch fix/fps-ids-limbs (2026-10-11)
- **D-R0. New clip, as asked.** The answer to "run it now?" was "make a new video", so I recorded clip 2 (`perf/record_clip2.py`, threaded) before any change and measured everything on it.
- **D-R1. Camera stays at 4 fps.** Three attempts to get MJPG from the Arducam failed (OpenCV 5.0 params at open, OpenCV 5.0 set-after-open, OpenCV 4.12): it always sends raw YUY2 at 4 fps (1 fps on 4.12). Idea dropped per the 3-failure rule. I did NOT test the Media Foundation backend because its camera numbering can differ and might open the laptop camera. Suggestion for you: try another USB port (USB 3) and check the Arducam in the Windows Camera app / AMCap for an MJPG mode; the old perf log measured 30 fps on this camera.
- **D-R2. GPU not usable; not touched.** The only GPU is the Intel UHD 620 (driver 27.20.100.8854). OpenVINO's GPU plugin fails to build (2026.4.1 and 2025.4.0, two attempts). Fix is a driver update, which I'm not allowed to do: update "Intel UHD Graphics 620" via Intel Driver & Support Assistant or HP's support page for this laptop, then run `perf\bench_models.py` again. Everything runs on OpenVINO CPU (proven in the trace: `openvino:CPU` for all 3 models).
- **D-R3. Targets the camera makes impossible.** Display FPS target "camera's full rate" is met (3.85 = what the camera gives). "Processed FPS >= 20 / p5 >= 15" can't be met: only 3.85 frames per second exist. I report the loop's capacity (19-24 fps average) to show the program itself is not the limit.
- **D-R4. Round 2 kept on its third attempt with two exceptions.** Overlap ID switches went 0.62 -> 0.93 (2 -> 3 switches) and alert times shifted, but people recall, device recall, limbs and AI rate all improved, and reverting would leave the AI at 0.3 checks/s. Later identical-code runs showed the ID-switch number swings 0.62-1.55 by noise alone.
- **D-R5. Tracking changes dropped after 3 failures** (shirt colours + unsure revive; body-part filter + unsure revive; shirt colours + body-part filter). The offline colour test proves shirt-only colours separate people better (0.68-0.91 vs 0.14), so this is the first thing to retry with a longer test clip.
- **D-R6. Alert mapping.** The old "phone" alert (which also fired for smart watch, earbuds, headphones) is now the "device" alert and fires on the same things. Paper and pen are new classes and never alert (`NOT_ALERT_ITEMS`). No thresholds changed.
- **D-R7. Video files keep the old loop.** The threaded runtime is for the live camera; `python -m app.main video.mp4` still checks a file step by step (repeatable, and the existing tests rely on it).
- **D-R8. Watch false positives measured on checked frames.** Each false device box on one of the 25 checked frames counts as one ~12 s stretch, scaled to 10 minutes. With 25 frames this is coarse.
- **D-R9. No fine-tuning.** Time went to the lag and tracking diagnosis; half-hidden phone recall (25%) is the main reason to fine-tune later on frames from a separate clip.
- **D-R10. Stopwatch delay test not run live.** It needs you to film a stopwatch. Replay delay (frame time to on-screen) is 66-78 ms average. Command in FINAL_REPORT.
